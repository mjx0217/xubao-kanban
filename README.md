# 沈阳基地 · 续报完成率看板

在线地址：https://mjx0217.github.io/xubao-kanban/

## 数据源

底表（Windows 下载目录 `D:\Downloads`）：

```
26-27学年秋续寒春_实时续报底表-YYYY-MM-DD HH_MM_SS.xlsx
```

脚本自动取文件名时间戳最新的一份，排除 `~$` 开头的 Excel 锁文件和「离线」底表。

## 指标口径

| 指标 | 公式 | 说明 |
|---|---|---|
| 在班人次 | 底表 `在班人次` | |
| 联报人次 | 底表 `联报人次` | |
| 联报达成 | 联报人次 | 等于联报人次，不做加总 |
| 目标人次 | 底表 `联报人次目标` | |
| **完成率** | 联报人次 ÷ 联报人次目标 | 看板核心指标，**官方口径** |
| 联报率 | 联报人次 ÷ 在班人次 | 官方「联报率」 |
| 目标覆盖率 | 目标人次 ÷ 在班人次 | 沈阳当前约 68.7% |
| 距离完标人次 | 目标人次 − 联报人次 | 前端列名「距离完标人次」（字段名仍为 `gap`）|
| 今日新增 | 逐行取 `max(续报人次日增, 联报人次日增)` 后求和 | 两个日增列高度重合，直接相加会双计 |

### ⚠️ 口径依据（不要改回加总）

底表自带透视表 `Sheet2`，里面是官方算好的「联报率」和「目标完成率」两列。
对 `Sheet2` 的 81 个明细行 + 10 个汇总行逐行比对验证：

- **目标完成率 = 联报人次 ÷ 联报人次目标**（最大误差 `3.11e-15`）
- **联报率 = 联报人次 ÷ 在班人次**（最大误差 `5.00e-16`）

看板算法与官方透视表逐行完全吻合。

**为什么不能「续报人次 + 联报人次」？**
底表 `sheet1` 里「续报人次」和「联报人次」在约 96.6% 的行数值完全相同
（同一批学员从两个产品视角各记一次），少数行甚至是 2 倍关系
（`(续报+联报)/在班` 最大到 2.0）。相加等于把同一批人重复计一遍，
会把完成率严重高估。

> 历史教训：2026-11-20 首次上线时曾误用「续报+联报」口径，
> 造成完成率虚高到 115.94%（两小时涨 28,158 人次而目标纹丝不动，明显失真），
> 当天已修正。

## 环比

`__lastRates` 字段记录与上一版数据的完成率差值（pp）。
仅当两版 `meta.period` 一致时才计算，避免跨周期（秋续寒春 ↔ 春夏续）串台。

### 完成率变化如何体现「和谁比」

前端三处同时标注对比基准：

1. **列头副标题**：完成率变化列下方显示「较 11-20 12:00 数据」
2. **图例说明**：右上角显示「完成率变化 = 较 11-20 12:00 数据」
3. **单元格内**：变化值下方小字显示「11-20 12:00数据 42.81%」（基准时间 + 当时完成率）

页脚同时显示「数据时间 2026-11-20 14:00 （对比 11-20 12:00 数据）」。

时间显示统一用缩写格式 `MM-DD HH:MM`（前端 `shortTime()`），不用完整日期。

数据来源：`__lastRates.<维度>.<名称>.lastCompleteRate`（上一版完成率），
与 `delta` 相加应等于当前完成率（已校验 320 条全部自洽）。

## 更新流程

```bash
cd /home/mjx/repos/xubao-kanban
python3 scripts/build_xubao.py --dry-run   # 只生成不推送
python3 scripts/build_xubao.py             # 生成 + 推送 GitHub
```

推送走 GitHub REST API（WSL 环境 `git push` 会挂死），脚本会自动从 `~/.git-credentials` 读取 token。

生成文件：
- `xubao_data.json` — 看板数据
- `xubao_data_last.json` — 上一版存档
